Installation

juphyter has two halves. The engine that runs your cells is PHP, and the transport that speaks the Jupyter protocol is a small Python module that runs inside ipykernel. Installing juphyter means putting a kernelspec where Jupyter looks for one, pointing at both.

A kernelspec belongs to the machine rather than to a project. There is one php kernel per user, whatever directory you installed from, so installing juphyter once for your user is the usual choice. The engine does not need to live in a project either: it starts in the document’s own directory and walks up for a vendor/autoload.php, so a document anywhere on disk gets a working PHP kernel.

Requirements

  • PHP 8.3 or later, from Homebrew, Herd, or a distribution package. That floor matches phibble and phplyr. phiz needs PHP 8.5, so plots are available only on a kernel running 8.5 or newer.
  • Composer.
  • Python 3 with jupyter and ipykernel 7.0 or later. The wrapper subclasses ipykernel.kernelbase.Kernel, which changed in version 7. This costs nothing extra in practice: JupyterLab is a Python application, and Quarto’s jupyter engine requires a Python Jupyter whatever kernel it drives.
  • Quarto, to render Quarto documents.
  • macOS or Linux. The kernel interrupts a running cell with POSIX signals, which the Windows PHP build does not provide.

pcntl is wanted rather than required. Without it the kernel runs and the stop button does nothing, so juphyter install checks the PHP binary it is about to name and says so rather than refusing to install.

Install

Copy the whole block:

# Does the Python that Quarto will use already have Jupyter?
py="$(command -v python3)"
"$py" -c 'import jupyter_client' 2>/dev/null || py=''

# juphyter. It is not on Packagist yet, so Composer reads the repository
# directly, which "no-api" does over git and without a GitHub token.
composer global config repositories.juphyter \
  '{"type":"vcs","url":"https://github.com/phpstats/juphyter","no-api":true}'
composer global require phpstats/juphyter:dev-main

# The juphyter command on PATH.
bin="$(composer global config bin-dir --absolute 2>/dev/null)"
export PATH="$bin:$PATH"
grep -qF "$bin" ~/.zshrc 2>/dev/null \
  || echo "export PATH=\"$bin:\$PATH\"" >> ~/.zshrc

# Jupyter, in a virtual environment, only when that Python has none. Quarto
# picks it up as the python3 on PATH.
if [ -z "$py" ]; then
  python3 -m venv ~/.venvs/juphyter
  ~/.venvs/juphyter/bin/pip install jupyterlab
  export PATH="$HOME/.venvs/juphyter/bin:$PATH"
  grep -qF '.venvs/juphyter/bin' ~/.zshrc 2>/dev/null \
    || echo 'export PATH="$HOME/.venvs/juphyter/bin:$PATH"' >> ~/.zshrc
  py="$HOME/.venvs/juphyter/bin/python"
fi

# The kernelspec, naming that Python and the PHP on PATH.
juphyter install --python "$py"

# Check: a Jupyter version, and php among the kernels.
quarto check jupyter

On a machine running bash, write ~/.bashrc in place of ~/.zshrc.

juphyter install prints where the kernelspec went and which Python, PHP, and engine it recorded:

Installed the juphyter kernel "php" for PHP 8.5.10.
  kernel.json  /Users/you/Library/Jupyter/kernels/php/kernel.json
  python       /Users/you/.venvs/juphyter/bin/python (ipykernel 7.4.0)
  php          /opt/homebrew/bin/php
  engine       /Users/you/.composer/vendor/phpstats/juphyter/bin/juphyter

If ipykernel is missing from that interpreter the command writes nothing and prints the pip install line that fixes it. The interpreter it picks is the one that owns the jupyter on your PATH, read from that script’s shebang, because that is the environment your Jupyter actually runs in. Use --python to name a different one.

Why the kernel is installed against Quarto’s Python

Quarto chooses its own Python, independently of the one that installed the kernel, and the interpreter it chooses is the one that has to have Jupyter, because Jupyter is what starts the kernel and collects its output. On a typical macOS machine the python3 on PATH is a Homebrew build with no Jupyter in it, and quarto render then fails on a document whose kernel is installed and working:

ERROR: Jupyter kernel 'php' not found. Known kernels: python3

The install block asks that interpreter for jupyter_client before anything else and names it in --python when it has it, so Quarto and the kernelspec agree on one Python and nothing needs overriding. When it has no Jupyter, the block builds a virtual environment and puts it first on PATH, where Quarto finds it as python3.

quarto check jupyter reports the interpreter Quarto chose, whether it has Jupyter, and the kernels it can see through it:

Path: /Users/you/.venvs/juphyter/bin/python
Jupyter: 5.9.1
Kernels: php, python3

A Jupyter: (None) line there is this failure, whatever jupyter kernelspec list reports. The kernel is not the problem in that case, and the kernelspec needs no reinstall. quarto check writes its report to standard error, so pipe it through 2>&1 before a grep.

A terminal opened before the shell startup file was edited still carries the old PATH, which is the usual reason this error outlives an install that went correctly otherwise.

QUARTO_PYTHON names an interpreter outright, for one shell or one project. Exporting it from a shell startup file is worth avoiding, because it takes precedence over an activated virtual environment and would therefore change the interpreter for every Quarto project on the machine.

Your first Quarto document

Write a document in any directory, with no project around it:

---
title: "PHP in Quarto"
jupyter: php
---

::: {#0ab98696 .cell execution_count=1}
``` {.php .cell-code}
echo "sum: ", array_sum(range(1, 10)), "\n";
PHP_VERSION;
```

::: {.cell-output .cell-output-stdout}
```
sum: 55
```
:::

::: {.cell-output .cell-output-display execution_count=1}
```
'8.5.10'
```
:::
:::

quarto render hello.qmd runs the cell and puts its output in the HTML. Cell options work as they do for any other engine, because PHP accepts # comments.

In JupyterLab, started with jupyter lab, the same kernel appears in the launcher under the PHP version it found.

Checking it worked

jupyter kernelspec list

The kernel should appear under the name you gave it.

The phpstats packages

None of them is a dependency of juphyter, which installs and runs with any subset of the family present, including none of it. The install above therefore runs plain PHP, and phibble tables and phiz plots need the packages added.

A second kernel gives them to a document in any directory:

for r in phibble phplyr; do
  composer global config "repositories.$r" \
    "{\"type\":\"vcs\",\"url\":\"https://github.com/phpstats/$r\",\"no-api\":true}"
done
composer global require --prefer-source "phpstats/phibble:^0.3" "phpstats/phplyr:^0.3"

juphyter install --name phpstats --display-name "PHP (phpstats)" \
  --autoload "$(composer global config home 2>/dev/null)/vendor/autoload.php"

Name that kernel in the front matter as jupyter: phpstats.

It is a second kernel rather than a change to the first because --autoload fixes one autoloader for every document it runs, which suits a document outside any project and breaks one inside a project. The php kernel keeps the default search described under Which dependencies a notebook sees, so a document inside a Composer project sees that project’s own packages.

The packages are not on Packagist, so each needs a repositories entry with "no-api": true, which makes Composer read the repository with git rather than through the GitHub API and so needs no token. --prefer-source is needed for the same reason, because a dist zipball still comes from the API.

Use the released ^0.3 tags rather than dev-main for these. phplyr requires phpstats/phibble ^0.3, which a dev-main phibble does not satisfy, so asking for dev-main on both fails to resolve.

phiz requires PHP 8.5 and has to be left out below that. On 8.5 or newer, add it with composer global require --prefer-source "phpstats/phiz:^0.3".

Inside a single project

Installing juphyter as a project dependency pins the kernel’s version with the project:

composer require --dev phpstats/juphyter
vendor/bin/juphyter install

The kernelspec it writes is still the machine’s, and it names that project’s copy of the engine. Two consequences follow. Running the same command from a second project replaces the first kernelspec, which juphyter install reports as Replaced, and deleting the project’s vendor directory leaves every notebook on the machine pointing at an engine that is gone. Give each project’s kernel its own --name to keep them apart.

Without Composer: the standalone PHAR

A standalone PHAR gives you a kernel on a machine with no Composer:

php juphyter.phar install

The kernelspec then names the PHAR as its engine, and the engine finds a project’s dependencies at run time by walking up from the notebook’s own directory. A PHAR install also copies the Python wrapper out of the archive and beside the kernelspec, because Python cannot import from inside a phar:// path.

Several PHP versions at once

Each kernel needs its own name, and the display name follows the version it finds:

juphyter install --name php83 --php /path/to/php83
juphyter install --name php85 --php /path/to/php85

That produces two kernels in the launcher, “PHP 8.3” and “PHP 8.5”. Pass --display-name to label them yourself.

An absolute --php path is recorded as you wrote it. That matters with Homebrew, where resolving the symlink would pin the kernelspec to a versioned path such as /opt/homebrew/Cellar/php/8.5.10/bin/php that brew upgrade removes. A bare name such as php8.4 is still resolved to an absolute path, since a kernelspec cannot rely on your PATH.

Where the kernelspec goes

juphyter install writes to the per-user Jupyter data directory, which is ~/Library/Jupyter/kernels on macOS and $XDG_DATA_HOME/jupyter/kernels or ~/.local/share/jupyter/kernels on Linux. JUPYTER_DATA_DIR and JUPYTER_PLATFORM_DIRS are both honored, as jupyter --paths reports them. --prefix PATH writes under PATH/share/jupyter instead, which is the layout jupyter kernelspec install --prefix produces.

juphyter uninstall removes a kernelspec, and only one that juphyter wrote. It refuses to delete somebody else’s kernel of the same name, as does a reinstall.

Which dependencies a notebook sees

The engine starts in the notebook’s own directory, walks up looking for vendor/autoload.php, and loads the first one it finds. A notebook anywhere inside a Composer project therefore sees that project’s packages with no configuration.

Two ways to override that search, and the most explicit one wins. JUPHYTER_AUTOLOAD in the environment comes first, which is what --autoload at install time records in the kernelspec. A juphyter.json beside the notebook, or anywhere above it, comes second, and can set the same thing along with two run-time settings:

{
  "autoload": "vendor/autoload.php",
  "memory_limit": "512M",
  "include_path": "lib"
}

Relative paths in that file resolve against the file’s own directory, so one juphyter.json at a project’s root serves every notebook beneath it.

Static images

Plots render as interactive charts in JupyterLab and in Quarto’s HTML output with nothing else installed. Rendering a Quarto document to PDF or Word needs a static image, which phiz produces with the vl-convert binary. Put it on your PATH, or name it in PHIZ_VL_CONVERT. Without it, a plot in a PDF falls back to its text description.

The Python package vl-convert-python is not a substitute: it ships a library and no executable, and phiz runs the binary.

Either override replaces the search rather than extending it. A kernel installed with --autoload loads that one autoloader for every notebook it runs, including a notebook that sits inside a Composer project of its own, so keep such a kernel under its own --name as The phpstats packages does.
